# Upgrade iSH to x86_64 Emulation Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Extend iSH so it can boot and run x86_64 Linux userland programs while preserving the current i386 behavior.

**Architecture:** Add explicit guest-ABI/guest-mode separation first, then introduce 64-bit guest types, ELF64 loading, x86_64 CPU state, long-mode decoding/execution, and x86_64 Linux syscall dispatch. Keep the existing Asbestos threaded-code engine as the shipping iOS-compatible execution engine; do not require JIT for x86_64 support.

**Tech Stack:** C, Meson, Asbestos threaded-code emulator, iSH userspace kernel, x86/x86_64 Linux ABI, ELF32/ELF64, existing e2e/ptraceomatic/unicornomatic-style test tools.

---

## Current Context / Assumptions

The current tree is heavily i386-oriented:

- `misc.h` defines `addr_t` and `uint_t` as `dword_t`.
- `emu/mmu.h` defines `page_t` as `dword_t`, `MEM_PAGES` as `1 << 20`, and `BAD_PAGE` as `0x10000`.
- `kernel/elf.h` has ELF64 constants but `struct elf_header`, `struct prg_header`, `struct aux_ent`, and `struct dyn_ent` are 32-bit layouts.
- `kernel/exec.c` rejects anything except `ELF_32BIT` and `ELF_X86`, builds a 32-bit stack, writes 32-bit auxv entries, sets `eip`/`esp`, and initializes only 32-bit registers.
- `kernel/calls.c` dispatches the i386 ABI: syscall number in `eax`, args in `ebx`, `ecx`, `edx`, `esi`, `edi`, `ebp`.
- `emu/cpu.h` models 32-bit general registers and `eip`/`eflags`, with existing XMM state that can be reused/expanded.
- `emu/modrm.h` only decodes 32-bit addressing via `modrm_decode32()`.
- `emu/decode.h` is macro-generated around `OP_SIZE` and i386 opcodes; it does not model REX prefixes, RIP-relative addressing, or registers `r8`-`r15`.
- `docs/architecture.md` documents the current 32-bit execution model.
- `docs/jit-engine-plan.md` documents why JIT is not a safe prerequisite for App Store/TestFlight iOS support.

Primary implementation rule: **x86_64 support should be added alongside i386 support, not as a destructive replacement.**

---

## Proposed Approach

1. Introduce an explicit guest ABI/mode layer (`i386` vs `x86_64`) before widening core types.
2. Split guest pointer/register/syscall types so 32-bit structs do not silently become ABI-incompatible.
3. Add ELF64 parsing and x86_64 process startup behind tests.
4. Add x86_64 CPU register state and accessors while preserving i386 register aliases.
5. Add long-mode decode support incrementally: REX prefixes, 64-bit operands, extended registers, and RIP-relative memory.
6. Add x86_64 syscall dispatch with separate table and ABI-specific copy-in/copy-out structs.
7. Bring up static x86_64 `hello` first; dynamic musl/Alpine comes later after TLS, signals, mmap, and loader-facing syscalls work.

## Milestone 2: Memory Model for 64-bit Guest Addresses

### Task 2.1: Design sparse page indexing

**Objective:** Remove the `MEM_PAGES == 1 << 20` assumption for x86_64 without exploding memory usage.

**Files:**
- Modify: `emu/mmu.h`
- Modify: `kernel/memory.h`
- Modify: `kernel/memory.c`

**Current issue:**
- 32-bit iSH uses 4 GiB / 4 KiB = `1 << 20` guest pages.
- x86_64 canonical user space is much larger; a flat page directory is not viable.

**Approach:**
- Keep the current two-level table for `GUEST_ABI_I386` initially.
- Add a sparse map abstraction for guest pages:
  ```c
  struct guest_page_key { uint64_t page; };
  struct guest_page_map;
  struct pt_entry *guest_page_get(struct mem *mem, uint64_t page);
  int guest_page_set(struct mem *mem, uint64_t page, struct pt_entry *entry);
  ```
- Choose implementation only after measuring complexity:
  - radix tree with 9-bit chunks; or
  - hash table keyed by `uint64_t page`; or
  - hybrid: keep current array for low 4 GiB and add sparse overflow map.

**Verification:**
- Existing i386 e2e tests must still pass.
- New tests should map/read/write a page above 4 GiB and verify low-page mappings still work.

### Task 2.2: Widen TLB and fault addresses

**Objective:** Make translations and fault reporting capable of 64-bit guest addresses.

**Files:**
- Modify: `emu/tlb.h`
- Modify: `emu/tlb.c`

- Modify: `kernel/calls.c`
- Modify: `emu/cpu.h`

**Implementation notes:**
- `mmu_ops.translate` should accept `guest_addr_t`.
- `cpu->segfault_addr` must become 64-bit.
- Logging format strings must use `PRIx64` or cast to `unsigned long long`.

**Tests:**
- Unit test for TLB miss and fault address above 4 GiB.
- i386 regression test for a normal page fault.

**Files:**

## Milestone 4: x86_64 CPU State

### Task 4.1: Add 64-bit register storage with 32-bit aliases

**Objective:** Represent `rax`-`r15`, `rip`, and `rflags` while preserving existing i386 code.

**Files:**
- Modify: `emu/cpu.h`
- Modify: code using direct `cpu->eax`, `cpu->eip`, etc. as needed
- Test: `tests/unit/cpu_regs_test.c`

**Implementation sketch:**
```c
enum reg64 {
    reg_rax, reg_rcx, reg_rdx, reg_rbx,
    reg_rsp, reg_rbp, reg_rsi, reg_rdi,
    reg_r8, reg_r9, reg_r10, reg_r11,
    reg_r12, reg_r13, reg_r14, reg_r15,
    reg64_none,
};

struct cpu_state {
    struct mmu *mmu;
    long cycle;

    union {
        qword_t regs64[16];
        struct {
            qword_t rax, rcx, rdx, rbx, rsp, rbp, rsi, rdi;
            qword_t r8, r9, r10, r11, r12, r13, r14, r15;
        };
    };

    qword_t rip;
    qword_t rflags;

    // Compatibility accessors or macros for existing i386 code should be
    // introduced carefully; direct union aliasing must preserve little-endian
    // behavior and x86_64 zero-extension rules.
};
```

## Milestone 6: x86_64 Syscall ABI

### Task 6.1: Add separate x86_64 syscall table

**Objective:** Dispatch x86_64 Linux syscall numbers without disturbing i386 table indices.

**Files:**
- Create: `kernel/calls_x86_64.c`
- Modify: `kernel/calls.c`
- Modify: `kernel/calls.h`

**ABI:**
- syscall number: `rax`
- args: `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`
- return: `rax`
- `syscall` instruction clobbers `rcx` and `r11` architecturally

**Implementation sketch:**
```c
typedef qword_t (*syscall64_t)(qword_t, qword_t, qword_t, qword_t, qword_t, qword_t);
extern syscall64_t syscall64_table[];
extern size_t syscall64_table_len;

static void handle_syscall64(struct cpu_state *cpu) {
    qword_t nr = cpu->rax;
    if (nr >= syscall64_table_len || syscall64_table[nr] == NULL) {
        cpu->rax = (qword_t) (sqword_t) _ENOSYS;
        return;
    }
    cpu->rax = syscall64_table[nr](cpu->rdi, cpu->rsi, cpu->rdx, cpu->r10, cpu->r8, cpu->r9);
}
```

**Initial table entries for static hello:**
- `0` `read`
- `1` `write`
- `60` `exit`
- `231` `exit_group`

**Next entries for dynamic musl:**

- `10` `mprotect`
- `11` `munmap`

- `21` `access`

## Risks and Tradeoffs

- **Scope is large:** x86_64 touches loader, CPU, decoder, memory, syscalls, signals, TLS, and tests. Treat as a multi-month port, not a single feature patch.
- **Do not make global typedefs 64-bit too early:** Widening `addr_t` globally will silently change i386 struct layouts and syscall behavior. Split ABI-specific types first.
- **Sparse memory is required:** A 64-bit address space cannot use the current fixed `MEM_PAGES` model naively.
- **Dynamic userland requires TLS and signals:** Static assembly hello is only the first milestone. Real x86_64 Alpine needs `arch_prctl`, `mmap`, `futex`, signal frames, and ABI-correct structs.
- **Instruction coverage can balloon:** Keep the first x86_64 instruction subset tiny and let e2e failures drive expansion.
- **JIT is not required and should not be coupled:** iOS distribution constraints make JIT a separate experimental track.
- **Compatibility must remain explicit:** Existing users expect i386 Alpine. x86_64 should be selected by ELF type/rootfs, not by breaking current roots.

## Open Questions

1. Should iSH support mixed i386 and x86_64 processes in one session, or should a rootfs/session choose one ABI at boot?
2. Should the memory model aim for full canonical x86_64 user address ranges immediately, or start with a documented low-address subset?
3. Should the 32-bit and 64-bit exec loaders live in one `kernel/exec.c` file or be split once ELF64 support lands?
4. Which libc/rootfs is the first official target: static musl fixtures, Alpine x86_64 minirootfs, or both?
5. Should `uname -m` report per-task ABI (`i686` vs `x86_64`) once mixed ABI support exists?
6. Is x86_64 signal support required before merging experimental support, or can it be milestone-gated behind static no-signal programs?
